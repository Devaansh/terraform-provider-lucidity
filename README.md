# terraform-provider-lucidity

Terraform provider for Lucidity (cloud storage optimization platform). 
Published to the public Terraform Registry as a community provider, built to Partner-tier quality

About Lucidity - https://www.lucidity.cloud/




```hcl
terraform {
  required_providers {
    lucidity = {
      source  = "luciditycloud/lucidity"
      version = "~> 0.1"
    }
  }
}
```



## Provider facts

- **Language/stack:** Go + Terraform Plugin Framework (NOT legacy SDKv2).
- **License:** MPL-2.0.
- **Publishing:** community provider from the Organization's GitHub repo.
  Releases signed with a dedicated GPG key held by the organization.
- **API docs:** `docs/api/` holds the Lucidity API references, one folder per
  module. `docs/api/legacy/` is the current API (authentication, tenants,
  temporary buffer); `docs/api/revamp/` is for the revamped API. Treat these
  as the source of truth for endpoints, fields, and error tables.

## Provider Authentication Management

The provider authenticates against Lucidity's revamped token endpoint,
`POST /v1/oauth2/token` ([docs/api/revamp/auth/auth.md](docs/api/revamp/auth/auth.md)),
with **one** of two credential types:

| Credential type | Who it is | What you give the provider |
|---|---|---|
| **User refresh token** | A person's dashboard login | `refresh_token` / `refresh_token_file` / `refresh_token_command`, or `LUCIDITY_REFRESH_TOKEN` |
| **Service account** (recommended for automation) | A non-human identity whose roles decide what it can do | `client_id` (or `LUCIDITY_CLIENT_ID`) plus `client_secret` / `client_secret_file` / `client_secret_command` (or `LUCIDITY_CLIENT_SECRET`) |

Either way, the provider exchanges the credentials for a 15-minute access
token, renews it before it expires by sending the same credentials again,
and never writes the credentials or tokens to state or logs.

**Getting a user refresh token**

1. Log into the Lucidity Dashboard
2. Click on settings (Bottom left)
3. Click on "API Key"
4. Click on "Create Key" to generate a refresh token (format `<accessKey>.<secretKey>`)
5. Supply the refresh token to this provider

The refresh token's expiry is set and managed in the dashboard.

**Getting service account credentials**

Service accounts, their roles and their credentials are created and managed
in the Lucidity dashboard (not through this provider). Creating a credential
gives you a `clientId` and a `clientSecret`. **The secret is shown only
once**, at creation: store it in your secret manager straight away. The
credential's expiry is also set and managed in the dashboard.

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://app.lucidity.cloud"
  lucidity_dashboard_account_name = "Acme Corp"
  client_id                       = "svc-abc123"
  client_secret_command           = "aws secretsmanager get-secret-value --secret-id lucidity/client-secret --query SecretString --output text"
}
```

**Rules**

- Use one credential type. Setting a refresh token source together with
  `client_id` or a client secret source fails at `terraform validate`.
- At most one source per secret: one of `refresh_token`,
  `refresh_token_file`, `refresh_token_command`; or one of `client_secret`,
  `client_secret_file`, `client_secret_command`.
- The provider block decides the type when it sets any credential
  attribute. The other type's environment variables are then ignored.
- With no credential attributes, the environment decides:
  `LUCIDITY_REFRESH_TOKEN`, or `LUCIDITY_CLIENT_ID` + `LUCIDITY_CLIENT_SECRET`.
  Both types set in the environment is an error, not a guess.
- `client_id` in the provider block with the secret in
  `LUCIDITY_CLIENT_SECRET` (or the other way round) is fine.

All the secret-store recipes below use `refresh_token_command` /
`refresh_token`; they work the same way for `client_secret_command` /
`client_secret`.

**API documentation notes (authentication).** Differences between Lucidity's
revamped auth API docs ([docs/api/revamp/auth/auth.md](docs/api/revamp/auth/auth.md))
and this provider, and what is still unconfirmed:

| Topic | API docs | This provider | Impact |
|---|---|---|---|
| Token endpoint | `POST /v1/oauth2/token` for users and service accounts. The doc lists `/public/v1/auth/tokens` and `/external/client/api/v1/auth/token` as replaced. | Uses `/v1/oauth2/token` | Existing refresh tokens keep working. The legacy `/external/api/v1/auth/user-token/refresh` (used by provider v0.1.x) is still live but will be deprecated: upgrade before it is. |
| Header on API calls | `Authorization: Bearer <token>` | Sends `Authorization: Bearer <token>` **and** the legacy `X-Authtype: lucidity_access_token` | The legacy tenant endpoints accept the new token (confirmed by Lucidity engineering). The extra header is harmless and will be dropped once confirmed unnecessary. |
| API host | The examples use `https://dash-back.lucidity.dev` (the dev host) | Keeps the dashboard URL → API host table unchanged for all five deployments | Every deployment is expected to serve `/v1/oauth2/token` on the same host, but only dev has been seen in the docs. |
| Service accounts | Supported: `clientId` + `clientSecret`; the secret is shown once | Supported (`client_id`, `client_secret*`, `LUCIDITY_CLIENT_*`) | Automation no longer has to run as one named Admin. Service accounts and their roles are managed in the dashboard. |
| Credential expiry | Not covered by the doc | — | Refresh tokens, client IDs and client secrets all expire; expiry is managed in the dashboard. Access tokens always last 15 minutes (compliance). |
| Renewal | No refresh token for service accounts: call the endpoint again with the same body | Re-sends the same credentials before the 15-minute expiry | None. |
| Response and errors | Wrapped in `{success, data / error, requestId}`; branch on `error.code` (`VALIDATION_ERROR`, `INVALID_REQUEST`, `UNAUTHORIZED`, `INTERNAL_ERROR`) | Reads the wrapped token; a 401 names which credential type was rejected; other errors keep their code and `requestId` | Quote the `requestId` to Lucidity support. |
| Refresh token format | `<accessKey>.<secretKey>`; a token without the `.` gets `400 INVALID_REQUEST` | No client-side check | Existing tokens already use this format. |



**AWS Option 1 - Secrets Manager (recommended):**

`refresh_token_command`, via the AWS CLI

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "aws secretsmanager get-secret-value --secret-id lucidity/refresh-token --query SecretString --output text"
}
```

Runs at configure time; the token never touches `.tf` files or Terraform
state. Requires the AWS CLI installed wherever `terraform` runs, AWS
credentials available in that environment (instance profile, IRSA, SSO
profile, etc.), and an IAM policy granting `secretsmanager:GetSecretValue` on
that secret's ARN. If the secret is stored as JSON rather than a plain
string, pipe through `jq`: `... --output text | jq -r .token`.


**AWS Option 2  -  `refresh_token`, fed from a data source**

```hcl
provider "aws" {
  region = "us-east-1"
}

data "aws_secretsmanager_secret_version" "lucidity_refresh_token" {
  secret_id = "lucidity/refresh-token"
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.aws_secretsmanager_secret_version.lucidity_refresh_token.secret_string
}
```

Works, but the fetched value gets written into Terraform state as that data
source's attribute (every data source result is persisted to state, not just
resources) — only as safe as your state's encryption/access controls. Also
requires configuring the `aws` provider just for this lookup.

Option 1 is preferred for exactly that reason: no bespoke per-backend client
code in the provider, and the secret never lands in state.

**Azure Option 1 - Azure keyvault (recommended):**

`refresh_token_command`, via the Azure CLI

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://web-azurepls.lucidity.cloud/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "az keyvault secret show --vault-name my-vault --name lucidity-refresh-token --query value -o tsv"
}
```

Requires the Azure CLI installed and authenticated (`az login`, a managed
identity, or a service principal already logged in) wherever `terraform`
runs, and the "Key Vault Secrets User" role (or a classic access policy with
`get` permission) on that secret.

**Azure Option 2: `refresh_token`, fed from a data source**

```hcl
provider "azurerm" {
  features {}
}

data "azurerm_key_vault" "this" {
  name                = "my-vault"
  resource_group_name = "my-resource-group"
}

data "azurerm_key_vault_secret" "lucidity_refresh_token" {
  name         = "lucidity-refresh-token"
  key_vault_id = data.azurerm_key_vault.this.id
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://web-azurepls.lucidity.cloud/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.azurerm_key_vault_secret.lucidity_refresh_token.value
}
```

Same state-encryption caveat as the AWS data-source option: the fetched
value is persisted to Terraform state as this data source's attribute.


**GCP Option 1 - Secrets Manager (recommended):**

```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://app.lucidity.cloud"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "gcloud secrets versions access latest --secret=lucidity-refresh-token"
}
```

Requires the gcloud CLI installed and authenticated (Application Default
Credentials or a service account already active) wherever `terraform` runs,
and `roles/secretmanager.secretAccessor` on that secret.

**GCP Option 2: `refresh_token`, fed from a data source**

```hcl
provider "google" {
  project = "my-project"
}

data "google_secret_manager_secret_version" "lucidity_refresh_token" {
  secret = "lucidity-refresh-token"
}

provider "lucidity" {
  lucidity_dashboard_url          = "https://app.lucidity.cloud"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token                   = data.google_secret_manager_secret_version.lucidity_refresh_token.secret_data
}
```

Same state-encryption caveat as the other data-source options above.


**AWS/Azure/GCP Option 3  -  HashiCorp Vault**


```hcl
provider "lucidity" {
  lucidity_dashboard_url          = "https://www.web.lucidity.dev/dashboard"
  lucidity_dashboard_account_name = "Acme Corp"
  refresh_token_command           = "vault kv get -field=token secret/lucidity"
}
```

Requires the Vault CLI installed wherever `terraform` runs, and Vault
authentication already established in that environment (`VAULT_ADDR` +
`VAULT_TOKEN`, AppRole, or whichever auth method your setup uses — the
provider just execs `vault`, it doesn't manage Vault auth itself), plus a
Vault policy granting `read` on that KV path.


**Option 4 (AVOID)  -  Hardcode token**

- **Avoid hardcoding the refresh token directly in a `.tf` file.** Even if you
  remove it later, it stays in your git history in plaintext forever.
- **Avoid `.tfvars` files for it.** Treat the `.tfvars` file exactly like the direct `refresh_token`
  attribute — same plaintext-on-disk risk — keep it out of version control
  (`.gitignore`), and prefer the `LUCIDITY_REFRESH_TOKEN` env var or one of
  the `refresh_token_command` recipes above instead.
- Token can be hardcoded in during testing. Remember to expire the token via the Lucidity Dashboard once testing is completed


## Lucidity Dashboard Account Management

Manages a cloud account as a Lucidity tenant: onboard it, modify it, deboard it.
Two objects: the `lucidity_tenant` resource and the `lucidity_tenants` data source.

| Cloud | Onboard / modify / deboard / import |
|---|---|
| AWS | Supported |
| Azure | Not yet supported by Lucidity (neither the legacy nor the revamped API) |
| GCP | Not yet supported by Lucidity (neither the legacy nor the revamped API) |

`lucidity_tenants` still lists every tenant on the account, whatever its cloud.

### Onboarding a new AWS account

```hcl
resource "lucidity_tenant" "example" {
  lucidity_dashboard_display_name = "example-account"
  lucidity_product_list           = ["AUTOSCALER"]

  cloud_entity_information {
    cloud_provider            = "AWS"
    cloud_provider_account_id = "123456789012"
    aws_iam_external_id       = "8f14e45f-ceea-4331-9f5e-111111111111" # generate your own; must match the IAM role's trust policy
    aws_iam_role_name         = "LucidityRole"
    aws_iam_policy_name       = "LucidityPolicy"
  }

  # Safety rails — defaults shown explicitly for visibility in code review.
  # Deboarding on Lucidity is IRREVERSIBLE via API: an INACTIVE tenant can
  # only be reactivated by Lucidity support, and deboarding an account with
  # running services causes immediate disruption.
  lucidity_dashboard_account_delete_protection = true
  # lucidity_account_destroy_behavior = "forget"   # consulted only if protection = false
}
```

Only AWS accounts can be managed through this provider today (see the
support table above); `cloud_provider` accepts `AWS` only.

### Modifying a tenant

| Field | Updatable in place? |
|---|---|
| `lucidity_dashboard_display_name` | Yes |
| `aws_iam_role_name` / `aws_iam_policy_name` (AWS) | Yes |
| `cloud_provider`, `cloud_provider_account_id` | No — different tenant, forces replace |
| `aws_iam_external_id` | Yes — Lucidity returns and accepts it now. **Update your IAM role's trust policy first**, then change the value: Lucidity re-validates by assuming the role and rejects the update otherwise |
| `lucidity_product_list` | No — not supported by Lucidity's update API; changing a value already in state forces replace |
| `aws_org_root_id` | No — no update mechanism exists yet; changing a value already in state is caught at `terraform plan` |

### Deboarding an account (`terraform destroy`)

Deboarding is **irreversible** — only Lucidity support can reactivate an
INACTIVE tenant. Three-tier safety model:

| `lucidity_dashboard_account_delete_protection` | `lucidity_account_destroy_behavior` | Result |
|---|---|---|
| `true` (default) | — | Hard error, no API call |
| `false` | `"forget"` (default) | Removed from Terraform state only — stays ACTIVE on Lucidity |
| `false` | `"deboard"` | Actually deboards the account — the only path to it |

### Listing tenants

```hcl
data "lucidity_tenants" "all" {}

output "active_tenant_ids" {
  value = [
    for t in data.lucidity_tenants.all.tenants : t.tenant_id
    if t.status == "ACTIVE"
  ]
}
```

### Importing an existing tenant

```sh
terraform import lucidity_tenant.<name> AWS/<account-id>
```

Write a resource block for the account first, then import. Import reads the
tenant's `aws_iam_external_id` and display name from Lucidity, so they no
longer need to be guessed; a mismatch with your config is reconciled in
place on the next `apply`. `lucidity_product_list` and `aws_org_root_id` are
not returned by Lucidity's List API yet, so after import they are *assumed*
to match your config (recorded, never compared, never forcing a replace).
`aws_iam_role_name` / `aws_iam_policy_name` are likewise reconciled by a
normal update on the next `apply`.

### Known behavior worth knowing

- **Onboard is never auto-retried on a 5xx, timeout or connection error.**
  Such a failure doesn't show whether the tenant was created, and re-sending
  a successful create only produces a misleading "already exists" conflict.
  Instead the provider re-lists tenants and decides: if the tenant exists and
  is ACTIVE it is adopted into state and any differing display name /
  external ID is synced via the update API; if it is INACTIVE you get an
  "already exists and is in inactive state — contact support" error; if it is
  not found you get an error with recommended actions (wait and re-apply, or
  check the dashboard and `terraform import`). An "already exists" error on a
  later apply means the same thing: `terraform import` the account.
- Onboard/update/deboard can take a while to show up in `lucidity_tenants` —
  a `terraform apply` will retry for up to 150s before erroring; a genuine
  success sometimes still needs a manual re-`apply` past that window.
- `skip_cloud_permission_check = true` skips the IAM-*permission* check
  only — it does **not** skip Lucidity's baseline cloud-account-reachability
  validation, which still runs regardless of this flag. An unreachable or
  invalid cloud account fails onboarding either way.
- Changing `aws_iam_role_name` or `aws_iam_external_id` is re-validated by
  Lucidity (it assumes the role), so a typo or a trust policy that wasn't
  updated first fails the apply. `aws_iam_policy_name` and the display name
  are not independently verified.
- A 401 from Lucidity on those updates doesn't say which check failed, so the
  error lists every possible cause (token, role name, trust policy, external
  ID, policy, permissions boundary/SCP, account ID, IAM propagation) to work
  through.

### API documentation notes (tenants)

The provider uses Lucidity's revamped Tenant Linking API
([docs/api/revamp/tenants/tenant-linking-api.pdf](docs/api/revamp/tenants/tenant-linking-api.pdf)):

| Call | Endpoint |
|---|---|
| List | `GET /v1/tenants` (every cloud) |
| Read one | `GET /v1/tenants/{tenantId}` |
| Onboard | `POST /v1/tenants/aws/onboard` |
| Update | `PATCH /v1/tenants/aws` |
| Deboard | `PUT /v1/tenants/aws/deboard` |

- **AWS only.** The `/v1/tenants/aws/...` endpoints replace the legacy
  `/external/client/api/v1/tenants` ones (same request fields, with the
  cloud moved into the path). Neither generation supports Azure or GCP;
  Lucidity will add them as `/v1/tenants/azure` and `/v1/tenants/gcp`. The
  provider no longer calls the legacy tenant endpoints.
- **Missing IAM permissions** at onboard now come back as a 400 naming the
  permissions; the provider shows them and suggests
  `skip_cloud_permission_check` only for custom permission sets.
- **Validation errors** include a `details` list (field and message); the
  provider shows it.
- **Unknown request fields are ignored** by the API. `aws_org_root_id` isn't
  in the revamped doc either, so it is still sent but has no documented
  effect.
- **The revamped endpoints require `X-Authtype`** (`403 FORBIDDEN` otherwise),
  which the provider sends.
- **Reads use get-by-ID** (`GET /v1/tenants/{tenantId}`) once `tenant_id` is
  in state, instead of listing every tenant. Right after `terraform import`
  (no `tenant_id` yet) the first read lists and matches on cloud + account.
  After onboard and update, the provider still lists until the change shows
  up (up to 150s).

Full test evidence: [docs/qa-testing/account-management.md](docs/qa-testing/account-management.md).
Full schema reference: [docs/resources/tenant.md](docs/resources/tenant.md), [docs/data-sources/tenants.md](docs/data-sources/tenants.md).


## Lucidity Scaling Policy Management

Scaling policies set the buffer and size limits Lucidity applies to an
instance's disks. Three objects:

- `lucidity_scaling_policy`: the policy itself. Every setting is updatable
  in place, and drift on any setting is detected.
- `lucidity_scaling_policy_attachment`: attaches a policy to **one**
  instance; destroying it detaches; drift is detected on refresh. A policy can be attached to many
  instances: use one attachment per instance, so each team can attach its
  own instances from its own configuration.
- `lucidity_scaling_policies` (data source): lists every policy.

```hcl
resource "lucidity_scaling_policy" "db" {
  name                      = "prod-db-volumes"
  min_buffer_in_gb          = 30
  max_buffer_in_gb          = 300
  ideal_utilization_percent = 80
  max_fs_size_in_gb         = 2000
  min_disk_sku_size         = 8
  max_disk_sku_size         = 64
}

resource "lucidity_scaling_policy_attachment" "orders_db" {
  policy_id = lucidity_scaling_policy.db.id
  instance_identifier {
    cloud_provider            = "AWS"
    cloud_provider_account_id = "123456789012"
    instance_id               = "i-0abc123def4567890"
  }
}
```

### API documentation notes (scaling policies)

Source: [docs/api/revamp/scaling-policies/scaling-policies-api.pdf](docs/api/revamp/scaling-policies/scaling-policies-api.pdf)
(`/autoscaler/v1/scaling-policies`).

**How attachments are checked.** On every refresh, the provider asks the
Instances API ([docs/api/revamp/scaling-policies/instances-api.pdf](docs/api/revamp/scaling-policies/instances-api.pdf),
`POST /autoscaler/v1/instances`) which policy the instance actually has:

- **Same policy:** nothing to do.
- **No policy, or a different one** (detached in the dashboard, moved to
  another policy, instance removed): the attachment is dropped from state
  with a warning, and the next `plan` shows it will be attached again, so
  the code stays the source of truth.
- **Import** is verified the same way: importing an attachment that doesn't
  exist fails.

| Topic | API docs | This provider |
|---|---|---|
| Create response | Doesn't echo `minDiskSkuSize`, `maxDiskSkuSize`, `attachedInstanceCount` (reads 0) | Reads the policy back with `GET /{id}` after create |
| Update (`PUT`) | Omitted `maxBufferInGb` / disk SKU sizes reset to 0 | Always sends all seven settings |
| Names | Unique per account (`409 CONFLICT`) | The error names the existing policy's ID and how to import it; a create that fails with a 5xx is recovered by looking the name up |
| Delete with attachments | Not described | Deletes as asked; what happens to attached instances is unconfirmed |
| Attaching an instance that already has another policy | Not described | Unconfirmed |
| Field ranges | `idealUtilizationPercent` 1–100; other ranges not documented | Checks 1–100, and that the other numbers aren't negative |
| `X-Authtype` | Optional here | Sent anyway (other modules need it) |

## Lucidity User Management

Read-only for now:

- `lucidity_users` (data source): lists the account's users, optionally
  filtered by `email` (substring), `role` or `status`.
- `lucidity_roles` (data source): lists the roles users can be granted.

```hcl
data "lucidity_users" "active" {
  status = "ACTIVE"
}

data "lucidity_roles" "all" {}
```

A `lucidity_user` resource (invite, change roles, remove) will follow once
the API can read, update and remove a single user.

### API documentation notes (user management)

Source: [docs/api/revamp/user-management/user-management-api.pdf](docs/api/revamp/user-management/user-management-api.pdf)
(`/v1/users`, `/v1/roles`).

| Topic | API docs | This provider |
|---|---|---|
| Single-user endpoints | `GET`, `PATCH` and `DELETE` on `/v1/users/{userId}` not available yet (users are identified by email) | No `lucidity_user` resource yet: without update and delete it couldn't change roles or remove users |
| Inviting users (`POST /v1/users`) | Available; account admins only | Not used until the resource exists; invite in the dashboard |
| Pagination | `page` (zero-based) and `pageSize` (1–100) | Fetches every page, 100 users at a time |
| `status` not set | Removed users are included as `DISABLED` | Same; set `status = "ACTIVE"` to leave them out |
| Account admins | `roleAssignments` is empty; admin is not a role | Shown as `is_account_admin = true` with empty `role_assignments` |
| Lucidity staff | Hidden from the list | Same |
